Outbound Lead-Response Automation

From Gmail to ActiveCampaign, for both soc-med and cold leads

This automation watches James's outbound follow-up threads in Gmail and, the moment a lead responds, routes the thread and updates the records behind it — all the way through to ActiveCampaign. It runs every minute inside james@myadventuregroup.com.au's mailbox and handles two lead channels, soc-med and cold, with identical logic. A genuine reply is sent to the sales team to action; a delivery failure is recorded and the matching deal is closed off automatically. This page explains the whole path, end to end.

The big picture

James sends outbound follow-up emails from his mailbox. Each follow-up thread lives under a Gmail label for its channel and stays there while he keeps following up. A small script checks those threads once a minute and reacts only to what the lead does:

  • The lead replies → the thread moves to the sales "to-action" label and the lead's record is stamped as replied (status 8A).
  • The email bounces or is blocked → the bounce is recorded, the lead's record is marked bounced (status 10A), and the deal is closed off in ActiveCampaign with an automatic note. The thread moves to a "closed" label.
  • James sends another follow-up → nothing moves; the thread waits for a real lead response.

The journey in one line: Gmail thread → every-minute check → Supabase (record the outcome) → ActiveCampaign (act on a bounce) → Gmail label move.

The two channels

Both channels behave the same way. They differ only in which Gmail label they watch and which Supabase records they update. Everything else — the sales "to-action" label, the "closed" label, the reply status, and the ActiveCampaign step — is shared.

Soc-med leads

  • Watched Gmail label: follow-up-sequence-soc-med
  • Thread record table: follow_up_sequence_threads
  • Source lead lists: ai_scraped_soc_med_leads, manually_found_leads

Cold leads

  • Watched Gmail label: follow-up-sequence-cold-leads
  • Thread record table: cold_leads_follow_up_sequence_threads
  • Source lead lists: manually_found_cold_leads, ai_verified_cold_leads

Shared by both channels

  • Lead-replied label: @-sales-to-action-outbound-lead-responses
  • Closed (bounced) label: follow-up-sequence-closed
  • The same bounce-to-ActiveCampaign step processes both channels' bounces.

How a thread is routed

Once a minute the script sweeps each channel's label. To stay fast, it only looks closely at threads that had activity in roughly the last 10 minutes. For each of those, it reads the last message in the thread and decides who sent it:

  1. A bounce or block? Checked first — a message from postmaster or the Mail Delivery Subsystem whose text says "Delivery has failed" or "Message blocked".
  2. A lead reply? Any external sender that isn't us and isn't an automated system sender.
  3. One of us? A message from our own domain (James or a colleague) means the thread simply stays put.

Because the decision is based on the latest message, James can keep following up as many times as he likes and the thread won't move until the lead actually does something.

Auto-replies and out-of-office messages from the lead's own address count as a response and will move the thread — they are treated as a genuine reply.

When a lead replies (status 8A)

This is the happy path — the lead has come back to us. The script does two things, in this order:

  1. Update the record first. In the channel's thread table, it finds the row for that Gmail thread and sets status = 8A with a fresh timestamp (Sydney local time).
  2. Then move the thread into @-sales-to-action-outbound-lead-responses so the sales team sees it and can action the response.

The record is updated before the label moves on purpose: if the update can't go through for any reason, the thread is left where it is and the next sweep tries again — so the Gmail label and the database never drift out of step.

When an email bounces (status 10A)

If the last message is a delivery failure or block, the lead never received the email, so the thread is closed off and the deal is tidied up in ActiveCampaign. The script works out which address bounced (the one our outbound message was sent to) and then runs three steps in order:

  1. Record the bounce in Supabase. It calls the channel's bounce function — process_bounced_lead for soc-med, process_bounced_cold_lead for cold. That function marks the matching source-lead record as bounced (status = 10A) and adds a row to the shared bounced_leads table, tagged with its lead_type — soc med or cold.
  2. Action it in ActiveCampaign. It then triggers the process-bounced-leads step, which handles every pending bounced record the same way, regardless of channel (see the next section).
  3. Move the thread into follow-up-sequence-closed.

As with the reply path, both Supabase steps run before the thread is moved. If either step fails, the thread stays in place and the whole sequence is retried on the next sweep. All the steps are safe to repeat, so a retry never double-records or double-closes anything.

What happens inside Supabase

Supabase is the system of record that sits between Gmail and ActiveCampaign. Three kinds of pieces are involved:

Thread tables (the reply path)

  • Soc-med: follow_up_sequence_threads
  • Cold: cold_leads_follow_up_sequence_threads
  • On a reply, the row matching the Gmail thread is set to status = 8A.

Bounce functions (the bounce path)

  • process_bounced_lead (soc-med) and process_bounced_cold_lead (cold) are twins: each updates its own source-lead lists to status = 10A and inserts a de-duplicated row into bounced_leads.
  • The difference is only which lists they read and the lead_type tag they write (soc med vs cold), so ActiveCampaign can tell the channels apart later.
  • They de-duplicate on the email address, so the same bounce is never recorded twice.

The shared bounce-to-ActiveCampaign step

  • process-bounced-leads is a single shared routine that reads the bounced_leads table and pushes each pending row to ActiveCampaign.
  • It doesn't care which channel a row came from — soc-med and cold bounces flow through exactly the same step.

What happens in ActiveCampaign

The final stop is ActiveCampaign, and it only comes into play on a bounce. For each recorded bounce, the shared step does two things to that lead's deal, each only once:

  • Adds a note to the deal explaining that the intro email to that address bounced and that the deal has been marked lost — noting it was done automatically.
  • Marks the deal as Lost so it drops out of the active pipeline.

Each part is stamped once it succeeds, so if the step runs again it skips anything already done. A lead reply does not touch ActiveCampaign — replies are handed to the sales team through Gmail to action personally.

Why it's safe and reliable

  • Record first, move second. Every database and ActiveCampaign step runs before the Gmail label is changed. A transient failure just leaves the thread in place to retry — the label and the records never fall out of sync.
  • Safe to repeat. Recording a bounce, closing a deal, and stamping a reply are all idempotent, so a retry can never double-process a lead.
  • Runs continuously, cheaply. The check runs every minute but only inspects threads with recent activity, so it stays light even when hundreds of follow-ups are open.
  • One shared logic, two channels. Soc-med and cold run through the same code; a channel is just a small configuration entry, which keeps their behaviour perfectly in step.
