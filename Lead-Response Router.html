Gmail Lead-Response Router

Outbound follow-up thread automation for James's mailbox

A Google Apps Script that runs inside James's Gmail mailbox and manages the outbound lead follow-up sequence. Once every minute it looks at the follow-up label and routes each thread based on what has happened to it — a lead replied, or a send bounced — moving the thread to the correct label, updating the follow-up tracking table when a lead responds, and handing bounced addresses off to a separate clean-up function. It runs entirely inside Gmail at no cost, with no servers, OAuth clients, or refresh tokens to maintain.

What it does

James starts outbound follow-up email threads to leads, and those threads sit under a "follow-up sequence" label while he keeps following up. This automation watches that label and acts only when something meaningful happens on a thread:

  • The lead replies — the thread moves to the "to-action" label so the team picks it up.
  • The send bounces or is blocked — the bounced address is handed to a clean-up routine and the thread is closed out.
  • Nothing yet (James is the last to send) — the thread stays put, waiting.

The three labels involved

  • Watched: follow-up-sequence-soc-med — where James's live outbound follow-ups live.
  • Lead replied: @-sales-to-action-outbound-lead-responses.
  • Bounced / blocked: follow-up-sequence-closed.

How it decides what to do

The automation is driven by the latest message in each thread, not by "a new email arrived". Once a minute it checks who sent the most recent message and routes accordingly:

  • James (our domain) sent last → the thread stays in the follow-up label. His own follow-ups never trigger a move; it waits for a genuine lead response.
  • Delivery failed / blocked → if the latest message is from postmaster or the Mail Delivery Subsystem and says "Delivery has failed" or "Message blocked", the bounced address is processed (see below) and the thread moves to the closed label. This check runs first, so a failure notice is never mistaken for a reply.
  • A lead replied → if the latest message is from an external sender (outside our domain, and not a bounce), the thread moves to the to-action label.

Why it is safe and self-correcting

  • No double-handling: once a thread is moved it loses the follow-up label, so it is never processed again. Later replies stay on the thread under its new label.
  • Action first: the database update or the bounce function runs before the labels are changed. If that step ever fails, the thread is left in place and retried on the next run — it is never moved out of sync.
  • Efficient: each run only looks closely at threads with activity in roughly the last ten minutes, so it stays fast and light even when the follow-up label holds many open threads.

When a lead replies

The thread is one that James is actively following up, so it is tracked in the follow_up_sequence_threads table (in the MAGTestProject Supabase project). When the lead replies, the automation updates that thread's row, matched on the Gmail thread ID, setting two columns:

  • status → 8A.
  • status_update_date → the current date and time (Sydney local time), so you can see exactly when the thread changed state.

Then the thread moves to the to-action label. If a replied thread happens to have no matching row in the table, that is logged as a harmless warning and the thread is still moved.

When a send bounces

Bounced leads are handled by a completely separate flow — they are not part of the follow_up_sequence_threads table. When a bounce is detected, the automation:

  1. Works out which address bounced — the external recipient that James's outbound message in that thread was sent to.
  2. Calls the process_bounced_lead database function, passing that email address, so the bounce clean-up routine can do its job.
  3. Moves the thread to the follow-up-sequence-closed label so it is not looked at again.

The bounce function is called before the thread is moved, so if it ever fails the thread is left in place and retried on the next run — the bounce is never silently dropped.

Setup (in James's mailbox)

The script must live under James's own Google account, because it acts on his mailbox. Setup is a one-time job in the Apps Script editor:

  1. Sign in as James at script.google.com and create a new project.
  2. Paste in the automation code and the project manifest (which pins the permissions it needs).
  3. Add the Supabase service key as a Script Property so the database update and bounce function call can run.
  4. Run the script once and approve the permissions prompt — this is the Google consent screen that grants access to Gmail and to make the Supabase calls.
  5. Run the one-time backlog pass to catch any threads that already have a reply or a bounce.
  6. Install the every-minute trigger so it runs automatically from then on.

Configuration reference

All the adjustable settings sit at the top of the script, so nothing needs to be hunted for in the logic:

  • Watched label — follow-up-sequence-soc-med.
  • Lead-reply label — @-sales-to-action-outbound-lead-responses.
  • Closed label — follow-up-sequence-closed.
  • Reply status — 8A (written to the tracking table on a lead reply).
  • Bounce function — process_bounced_lead, called with the bounced email.
  • Our domain — myadventuregroup.com.au; a last message from here counts as "us", not a lead.
  • Activity window — how far back a scheduled run looks for fresh activity (about ten minutes).
  • Timestamp timezone — Australia/Sydney, used to stamp status_update_date.

Label names are matched flexibly, so they still work whether Gmail displays them with spaces or hyphens.

Monitoring and turning it off

Checking it is working

  • Open the Executions view in the Apps Script editor to see each run, how many threads were moved or bounced, and any warnings.
  • For a lead reply, confirm the thread's row in follow_up_sequence_threads shows status 8A and a fresh status_update_date.
  • For a bounce, look for the log line confirming process_bounced_lead was called with the bounced address.

Pausing it

Delete the every-minute trigger (or run the built-in "delete triggers" function). The code can stay in place — with no trigger, it simply never runs — and re-adding the trigger switches it back on.

Good to know

  • An auto-reply / out-of-office from a lead counts as a response and will move the thread; genuine bounces from mail-system senders are handled by the bounce path instead.
  • If a bounced recipient can't be worked out from the thread, it is left in place and a warning is logged rather than guessing.
  • If James ever sends from an address outside our domain, that address should be added to the "treat as us" list so his messages are not mistaken for a lead reply.
